## 1. Résumé

Le dossier `apps/api` existe : c'est la future API de Kemdia (NestJS 12). Elle ne sert encore **aucune donnée métier** :
elle démarre, vérifie sa configuration, répond au contrôle de santé, et pose les règles que tous les modules suivront
(sécurité HTTP, journaux, format des erreurs, organisation en couches). Le module `catalog` s'appuiera dessus au S3-T03.

## 2. Fonctionnalités livrées

| Élément                  | Ce que ça fait, en simple                                                                                                           | Fichiers principaux                             |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| Configuration vérifiée   | Au démarrage, chaque variable (port, version, origines autorisées…) est contrôlée. Une erreur ⇒ l'API ne démarre pas, message clair | `src/config/env.ts`, `.env.example`             |
| Contrôle de santé        | `GET /api/health` renvoie `{ status, version, environment }`, comme celui du site                                                   | `src/health/`                                   |
| Adresses versionnées     | Les routes métier seront sous `/api/v1/…` ; une future v2 pourra coexister                                                          | `src/http/configure-app.ts`                     |
| Erreurs uniformes        | Toutes les erreurs ont la même forme JSON (norme RFC 9457) ; une panne imprévue ne montre jamais de détail technique                | `src/http/problem-details.filter.ts`            |
| Journaux                 | Une ligne JSON par requête : méthode, chemin, statut, durée, identifiant. **Ni paramètres d'URL, ni corps, ni en-têtes**            | `src/http/logging.ts`                           |
| Organisation des modules | Chaque module aura 4 couches (`domain`, `application`, `infrastructure`, `interface`) ; un test refuse les mauvaises dépendances    | `src/modules/README.md`, `test/architecture.ts` |
| Intégration au monorepo  | `pnpm dev` lance le site **et** l'API ; lint, types, tests et build de l'API tournent dans la CI                                    | `turbo.json`, `.github/workflows/ci.yml`        |

**Exemple de configuration refusée** :

```
$ NODE_ENV=production PORT=abc node dist/main.js
Configuration invalide : l'API ne peut pas démarrer.
  - PORT : Entrée invalide : nombre attendu, NaN reçu
Voir apps/api/.env.example pour la liste des variables.
```

La valeur fautive n'est jamais recopiée : elle pourrait être un mot de passe collé par erreur.

**Exemple de ligne de journal** (requête vers une adresse inconnue avec `?tel=077123456`) :

```json
{
  "level": 40,
  "service": "kemdia-api",
  "version": "sha-local",
  "req": { "id": "00bf8b9e-…", "method": "GET", "path": "/api/v1/rien" },
  "res": { "statusCode": 404 },
  "responseTime": 6
}
```

Le numéro de téléphone présent dans l'adresse n'apparaît pas.

## 3. Décisions techniques

[ADR-0007](../architecture/adr/0007-socle-api-nestjs.md) — en résumé :

- **NestJS 12** est livré en _modules ES_ (le format moderne de JavaScript). On l'adopte tel quel ;
  conséquence visible : les imports internes se terminent par `.js` même dans les fichiers `.ts` (règle de Node.js).
- **Vitest**, comme pour le site : un seul outil de test dans tout le dépôt.
- **Zod** pour la configuration, testable sans démarrer NestJS.
- **Test d'architecture** plutôt que des règles ESLint : il lit les `import` et vérifie les vraies dépendances entre couches et modules.

## 4. Sécurité

| Mesure                                                                                                    | Risque couvert                                  |
| --------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| Configuration validée ; `debug` interdit en production ; version obligatoire en production                | Mauvais réglage, fuite de données dans les logs |
| CSP la plus stricte possible (`default-src 'none'`), `X-Frame-Options: DENY`, HSTS, sans `X-Powered-By`   | LOW-03 de l'ancien audit, empreinte technique   |
| CORS **fermé** par défaut (le site appelle l'API depuis le serveur, pas depuis le navigateur)             | Appels de l'API par un site malveillant         |
| Corps JSON limité à 100 Ko                                                                                | Saturation du serveur                           |
| 404 qui ne recopie pas l'adresse ; 500 générique, détail seulement dans les journaux                      | XSS réfléchie, fuite d'informations             |
| Champs sensibles (`password`, `otp`, `phone`, `email`, `token`, `cookie`…) masqués s'ils sont journalisés | Données personnelles (loi n°001/2011)           |
| Identifiant de requête (`X-Request-Id`) : celui de Caddy s'il est valide, sinon un nouveau UUID           | Injection dans les journaux, support client     |

`pnpm audit --prod` : 0 vulnérabilité.

**Risque restant** : aucune limitation de débit pour l'instant (prévue au S3-T04).

## 5. Qualité

- **35 tests** de l'API (Vitest + Supertest) : configuration (11), journaux (3), HTTP (13 : en-têtes, CORS, erreurs, versionnement), architecture (8).
  Couverture des lignes : **98,7 %**.
- Vérifié à la main : construction (`pnpm build`), démarrage réel en mode production, arrêt propre sur `SIGTERM`,
  refus de démarrer avec une configuration fausse (code de sortie 1), mode développement (`pnpm dev`).
- Site : 120 tests toujours verts, aucun changement de code.
- L'image Docker du site n'installe plus que ses propres dépendances (`--filter @kemdia/web`) : l'ajout de l'API ne la grossit pas.

## 7. Limites connues / dette technique

- Le contrôle de santé ne vérifie pas encore la base de données (elle arrive au S3-T02).
- Pas encore d'image Docker de l'API (S3-T06) ni de déploiement (S3-T07).
- Si plusieurs variables sont fausses, les règles propres à la production (`APP_VERSION`, HTTPS) ne sont signalées
  qu'une fois les erreurs de format corrigées : comportement de Zod, sans conséquence sur la sécurité.
