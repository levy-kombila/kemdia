## 1. Résumé

Le Sprint 3 est terminé : Kemdia a maintenant **un vrai backend**. Le catalogue (112 catégories, 50 produits, leurs variantes et leur stock)
vit dans **PostgreSQL**, il est servi par une **API NestJS** documentée, et le site ne lit plus rien d'autre.
La même chose tourne **en ligne, gratuitement** (Render + Neon), mise à jour à chaque fusion.

```
Visiteur ──► Site Next.js ──(HTTPS + clé interne)──► API NestJS /api/v1 ──► PostgreSQL 18
             kemdia-1.onrender.com                    kemdia-api.onrender.com    Neon (Francfort)
```

Le jalon **v0.3.0** peut être étiqueté (§8).

## 4. Sécurité

- **Aucun secret dans Git** : adresse de la base et clé interne uniquement dans les `.env` locaux (ignorés) et les réglages Render ; GitHub ne connaît que les deploy hooks.
- Configuration vérifiée **au démarrage** (API et site) : une erreur de réglage arrête le service avec un message qui nomme la variable, jamais sa valeur.
- API : en-têtes de sécurité, limitation de débit, requêtes SQL bornées dans le temps, requêtes paramétrées (injection testée), erreurs sans détail interne.
- Images Docker : non-root, lecture seule, scannées par Trivy à chaque PR ; `pnpm audit` à 0 vulnérabilité de production.
- Données de démonstration **refusées en production** (import et démarrage de démo), vérifié en CI.

## 7. Ce qui a été appris

- **Mesurer avant d'optimiser** : le profileur a montré que l'essentiel du blocage de l'accueil était la mise en page, pas le JavaScript ;
  et que l'enregistrement de Playwright faussait la mesure.
- **Vérifier en ligne, pas seulement en local** : la démo a révélé des réalités (port 5433 sous Windows, réveil des services gratuits,
  bascule de Render qui renvoie un 502 quelques secondes) que la CI ne voyait pas. Chacune a donné un correctif et une ligne dans les guides.
- **Ne jamais écraser un fichier `.env`** sans le lire : désormais, toute modification d'un `.env` est expliquée et validée avant d'être faite.

## 8. Étiqueter la version v0.3.0 (toi, après la fusion de cette PR)

Le pipeline de release ne se déclenche que pour le propriétaire du dépôt. Dans PowerShell, une commande par ligne :

```powershell
cd D:\React\kemdia
git checkout main
git pull
git tag v0.3.0
git push origin v0.3.0
```

Le workflow **Release** vérifie que le commit est sur `main` et que sa CI a publié les images, puis il **étiquette ces mêmes images** `v0.3.0`
(site et API, sans reconstruction) et crée la **Release GitHub** avec la liste des PR. Le déploiement en production est ignoré tant
qu'il n'y a pas de serveur (S7) : c'est normal.
