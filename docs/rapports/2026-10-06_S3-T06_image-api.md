## 1. Résumé

L'API a maintenant **son image Docker**, construite et vérifiée par la CI comme celle du site, et publiée sur GHCR à chaque fusion.
La même image sait aussi **mettre la base à jour** (migrations) : au déploiement, on lance d'abord les migrations, puis l'API.
Si les migrations échouent, la nouvelle API ne démarre pas et l'ancienne continue de servir.

La première partie de la tâche (« tests d'intégration avec une base PostgreSQL éphémère en CI ») était déjà faite au S3-T02 :
le job `API — migrations et intégration` tourne sur chaque PR depuis.

```
Déploiement d'une nouvelle version de l'API (même image, mêmes variables) :

  1. node dist/database/migrate.js   → « Migrations de la base : terminées, la base est à jour. »   (code 0)
  2. node dist/main.js                → API prête ; /api/health → "database":"ok"

  Si l'étape 1 échoue (code ≠ 0) : l'étape 2 n'a pas lieu.
```

## 2. Fonctionnalités livrées

| Élément                | Ce que ça fait, en simple                                                                                                                      | Fichiers principaux               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| Image de l'API         | Construite depuis la racine du dépôt ; ne contient que le code compilé et les dépendances de production ; utilisateur non-root                 | `apps/api/Dockerfile`             |
| Script de migration    | Vérifie la configuration **comme l'API** (même message, code 1), puis lance l'outil officiel `prisma migrate deploy` ; n'affiche aucune valeur | `src/database/migrate.ts`         |
| Moteur de migrations   | Téléchargé **pendant la construction**, pour Alpine ; la construction échoue s'il manque. Rien n'est téléchargé en production                  | `scripts/fetch-schema-engine.mjs` |
| Tout en local          | `docker compose up --build` : base → migrations → API → site, avec les images de production                                                    | `docker-compose.yml`              |
| CI                     | Nouveau job : construction, scan Trivy, migrations sur une base **vide**, relance sans effet, refus d'une configuration fausse, API démarrée   | `.github/workflows/ci.yml`        |
| Publication et release | `ghcr.io/levy-kombila/kemdia/api:sha-<commit>` à chaque fusion ; la release étiquette **le site et l'API** avec la même version                | `ci.yml`, `release.yml`           |
| Mises à jour           | Dependabot surveille aussi l'image de base de l'API                                                                                            | `.github/dependabot.yml`          |

## 3. Décisions techniques

[ADR-0012](../architecture/adr/0012-image-api-migrations.md) — en résumé :

- **Une seule image pour l'API et ses migrations** : le code et les migrations d'une même version voyagent ensemble.
- **L'outil officiel de Prisma**, pas un programme maison. Découverte utile : `@prisma/client` emporte de toute façon l'outil Prisma
  (dépendance « pair »). `prisma` passe donc en dépendance de production : c'est explicite au lieu d'être accidentel.
- **Migrations avant l'API, jamais au démarrage de l'API** : avec plusieurs instances, elles migreraient en même temps,
  et une migration longue bloquerait le contrôle de santé.
- **« Ajouter d'abord, supprimer plus tard »** : une migration ne doit pas casser la version précédente de l'API,
  car le retour arrière automatique redémarre l'ancienne image sur la base déjà migrée. Règle ajoutée au guide, avec un exemple.

## 4. Sécurité

| Mesure                                                                                                       | Risque couvert                              |
| ------------------------------------------------------------------------------------------------------------ | ------------------------------------------- |
| Utilisateur `kemdia` (non-root), système de fichiers en lecture seule, aucun privilège Linux (vérifié en CI) | Prise de contrôle du conteneur              |
| Fichiers de l'application appartenant à root : l'API ne peut pas modifier son propre code (vérifié en CI)    | Code modifié par une faille                 |
| Sans npm ni corepack, système Alpine mis à jour, **Trivy** bloque toute faille critique ou haute corrigeable | Image vulnérable                            |
| Migrations refusées en production si `DATABASE_URL` manque (l'adresse de développement est refusée)          | Production branchée sur une base de test    |
| Adresse de la base jamais affichée (Prisma masque aussi le mot de passe : `<REDACTED>`)                      | CRIT-02 (fuite d'identifiants)              |
| Aucun appel aux serveurs de Prisma à l'exécution (`CHECKPOINT_DISABLE`), moteur embarqué                     | Fuite d'informations, dépendance à Internet |
| Migration plus longue que 10 min interrompue (code 1)                                                        | Déploiement bloqué indéfiniment             |

`pnpm audit --prod` : 0 vulnérabilité (l'outil Prisma est désormais compté dans la production ; les correctifs imposés au S3-T02 s'appliquent).

## 7. Limites connues / dette technique

- **L'API n'est pas encore en ligne** : son image est publiée, mais rien ne la déploie. Démo Render au **S3-T07**, serveur de production au **S7**.
- **Image assez lourde** (environ 550 Mo décompressée d'après ma simulation ; taille exacte dans le résumé du job de la CI) : l'outil Prisma
  et sa console d'administration pèsent ~200 Mo. Sans effet sur la mémoire de l'API ; à réduire si Prisma sépare un jour ces parties.
- **Données de démonstration** : `db:seed` n'est pas dans l'image (il a besoin d'outils de développement). En local, il se lance depuis le poste ;
  pour la démo Render, à traiter au S3-T07.
- Un seul rôle PostgreSQL pour les migrations et l'API : deux rôles distincts au S7 (déjà prévu).
- Démo Render gratuite : la « commande avant déploiement » de Render ne semble pas proposée sur l'offre gratuite (à vérifier au S3-T07).
  Sinon, les migrations seront lancées depuis la CI, ou au démarrage du conteneur en dernier recours.

## Comment essayer (Docker Desktop requis, `pnpm dev` arrêté)

Commandes à taper une par une (PowerShell compris) :

```bash
docker compose up --build
pnpm --filter @kemdia/api db:seed
```

Dans les journaux : `api-migrate` affiche « la base est à jour » puis s'arrête (code 0), et l'API démarre ensuite.
Pour que le site lise l'API, ajouter `API_INTERNAL_KEY=<clé>` dans un fichier `.env` à la racine du dépôt
(guide : [base-de-donnees.md §4](../guides/base-de-donnees.md#4-tout-lancer-avec-les-images-de-production-s3-t06)).
