## 1. Résumé

La recherche pardonne maintenant les fautes de frappe et propose des suggestions pendant qu'on tape :

- **Fautes de frappe** : « sennhieser » trouve les produits Sennheiser, « écuteurs beats » trouve les écouteurs Beats.
  La correction ne se fait que si les mots tapés ne trouvent **rien** ; la page le dit et propose de chercher
  exactement ce qui a été tapé ;
- **Suggestions** : dès 2 lettres, après un quart de seconde sans frappe, jusqu'à 2 rayons, 2 marques et 4 produits
  (photo et prix) ; utilisables au clavier (flèches, Entrée, Échap) et avec un lecteur d'écran ;
- Le champ marche toujours **sans JavaScript** (simple formulaire), comme avant.

```
[ senn                          🔍 ]          Résultats pour « sennhieser »
 Marque   Sennheiser                          Aucun résultat pour « sennhieser ». Résultats pour
 [img] Sennheiser Écouteurs sans-fil Pro       « sennheiser ». Chercher exactement « sennhieser »
                              45 000 FCFA
```

## 3. Décisions techniques

Choix du 2026-10-23 : fautes de frappe avec **pg_trgm dans PostgreSQL** ; recherche approchée **seulement si rien ne
correspond** ; suggestions **produits + rayons + marques** ; **dès 2 lettres, après 250 ms**.

- **Deux étapes pour corriger** : la base propose des mots qui se ressemblent (groupes de 3 lettres, index), puis
  l'API choisit le plus proche en comptant les fautes ; une **inversion de deux lettres compte pour une faute**
  (« ipohne » → « iphone »). Tolérance : 1 faute jusqu'à 4 lettres, 2 jusqu'à 7, 3 au-delà ; pas de correction sous
  3 lettres.
- **Prudence** : un mot déjà présent dans le catalogue n'est jamais changé ; si un seul mot n'a pas de remplaçant
  proche, rien n'est corrigé (mieux vaut « aucun résultat » qu'un résultat hors sujet).
- **Même décision pour la liste et les compteurs** : elle ne dépend que des mots, de la catégorie et de la page
  (pas des filtres du client).
- **Suggestions par le serveur du site** : le navigateur n'appelle que le site (CSP inchangée) ; le site transmet
  l'adresse du visiteur pour que la limite de l'API compte par visiteur.
- **Pas de schémas Zod dans le navigateur** pour lire les suggestions : le champ est sur toutes les pages, une
  vérification légère suffit (le serveur du site a déjà vérifié la réponse avec le schéma).
- Décision complète : [ADR-0053](../architecture/adr/0053-recherche-suggestions-fautes.md).

## 4. Sécurité

### Relecture indépendante (agent séparé, avant la PR) : 0 haute, 2 moyennes, 3 basses, 2 infos — corrigées sauf 1 info

| Problème relevé                                                                                                                    | Correction                                                                                                                        |
| ---------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Moyenne : jusqu'à 8 requêtes en parallèle par recherche (une par mot), chacune avec sa connexion : 2 recherches bloquaient la base | **Une seule requête** pour tous les mots (une seule connexion)                                                                    |
| Moyenne : la page de résultats, relayée par le site sans limite par visiteur, pouvait déclencher des corrections sans fin          | **120 corrections en base par minute** au plus (tous visiteurs), puis recherche telle quelle ; correction **gardée 30 s** ; testé |
| Basse : sans `CLIENT_IP_HEADER` configuré, le relais des suggestions n'avait aucune limite                                         | Compteur commun « inconnue » dans ce cas                                                                                          |
| Basse : la limite réelle était de 180 par minute via le site (×3), pas 60 comme documenté                                          | Limite à **20 par adresse**, soit **60 par visiteur** via le site ; documentation alignée                                         |
| Basse : des mots corrigés de plus de 100 caractères faisaient refuser la réponse par le site (page d'erreur)                       | Pas de correction au-delà de 100 caractères                                                                                       |
| Info : deux mots justes qu'aucune fiche ne réunit pouvaient voir l'un d'eux « corrigé »                                            | La requête dit si chaque mot est déjà dans le catalogue : jamais corrigé ; testé (« beats sennheiser »)                           |
| Info : index créé sans `CONCURRENTLY` (bloque les écritures sur les fiches pendant sa création)                                    | Accepté et noté (§ 7) : quelques instants avec le catalogue actuel                                                                |

Sans problème selon la relecture : aucune injection SQL (requête paramétrée, mots réduits à `[a-z0-9]`) ; seules les
fiches visibles servent (publiées, non fusionnées, avec une offre visible) ; aucun XSS (textes affichés par React) ;
adresses des suggestions construites par le site (adresse vérifiée, marque encodée), pas de redirection ouverte ;
entrées bornées (100 caractères, 8 mots, 30 lettres) ; réponses d'erreur jamais mises en cache ; le texte tapé
n'est jamais écrit dans les journaux.

## 7. Limites connues / dette technique

- **Cache et budget des corrections en mémoire** : ils repartent de zéro au redémarrage et ne tiennent pas avec
  plusieurs instances de l'API.
- **Index créé sans `CONCURRENTLY`** : les écritures sur les fiches attendent pendant sa création (quelques instants).
- **Pas de boutiques dans les suggestions** : elles viendront avec S7.5-T07.
- **Pas de synonymes** (« portable » / « téléphone ») : seules les fautes de frappe sont corrigées.
